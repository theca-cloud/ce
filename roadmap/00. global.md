# Global roadmap

From an empty repo to the first CE release. Each step gets its own detailed file (`01. ...`, `02. ...`), written right before implementing it. Scope and design: see `../docs` (`ROADMAP.md` item 4, `decisions.md`: Repository, CI and releases; Architecture, the web app's CORS).

The order: the image first (what everything else runs), tested in CI before anything ships; then what a self-hoster runs it with; S3 last, being the optional part.

## Steps

| # | Step | Done when |
|---|---|---|
| 1 | **The image** | CI builds the CE image from the pinned `web` (and the `core` its label names), smoke-tests it, and publishes `rc` tags from `dev` |
| 2 | **The compose** | From two downloaded files (`docker-compose.yml`, `.env`) to the setup link, then to a running instance behind HTTPS, with backups documented |
| 3 | **S3 with Garage** | An overlay adds Garage, its bucket, key and CORS rule; the browser uploads and downloads through presigned URLs; CI covers it |
| 4 | **Two-way sync** | The `rclone bisync` documentation, tried end to end |
| 5 | **First release** | The CE image `0.1.0` is published, saying which `web` and `core` it holds |

## Contents

1. **The image**:
    - **The pin**: `WEB_VERSION` in the `Dockerfile` (an `ARG` default, the one place it's written). `core`'s version is read from the `web` image's label `org.theca.core` (`docker buildx imagetools inspect`) by `scripts/release-ci.sh`, never written here.
    - **The `Dockerfile`**: `FROM core:<v>`, `COPY --from=web:<v> /web /web`, `ENV WEB_DIR=/web`, labels `org.theca.web` and `org.theca.core`. Distroless, nonroot, `HEALTHCHECK` and entrypoint inherited from `core`'s image. amd64 and arm64: nothing compiled, both are copies.
    - **The smoke test** (`scripts/smoke.sh`, in CI against the freshly built image, Postgres as a service): the server starts and migrates, `/` and a deep link answer `index.html`, `/api/version` is the expected `core`, the setup through the API, a file in and out through WebDAV. The web's and core's own suites already test the parts: this only proves the pair is assembled right.
    - **Tooling** copied from `../web`: `scripts/ci.sh`, `.woodpecker/` (`ci.yaml`, `release.yaml`), `scripts/release.sh` and `release-ci.sh`, `cliff.toml`, the pre-push hook. The version lives in a `VERSION` file (no `package.json` or `Cargo.toml` here).
2. **The compose** (`docker-compose.yml` and `.env.example`, what self-hosters copy):
    - The CE image (by major tag) and Postgres 18 (`--locale-provider=builtin --builtin-locale=C.UTF-8`), on an internal network, Postgres never published.
    - **Storage: the filesystem backend by default** (a volume, `/data/files`): no second origin, no CORS, no init. The wizard still offers S3 (and every later backend), and several backends at once.
    - **No script to run**: `.env` holds `PUBLIC_URL` and `POSTGRES_PASSWORD` (hex: it goes into a URL); the database URL is a compose `config` with inline content built from it (`DATABASE_URL__FILE` points there), the keys live in a volume and the server generates them. Then `docker compose up -d`, and `docker compose logs theca` for the setup link.
    - **A reverse proxy with HTTPS is required**, and not bundled: the README says so up front, with a Caddy example and `TRUSTED_PROXIES`. The web app downloads through a Service Worker, which needs a secure context (only `localhost` is exempt).
    - **Backups** (decisions.md, Disaster recovery): `pg_dump`, the files volume, and `data.key` (lost = every TOTP set up again). Upgrades: pull, restart (migrations at startup, transactional).
    - **In `core`**: a missing key file is generated like an empty one (today only an existing empty file is), so the keys' volume needs nothing written first. **In `web`**: the setup wizard adds several storages, the first the default (the API already takes a list). Both reach the CE through a `web` patch release pinning the new `core`.
3. **S3 with Garage** (`docker-compose.s3.yml`, an overlay):
    - Garage single node, its config from `.env` (its RPC secret and admin token); an init service creating the layout, the bucket and the key (through Garage's admin API: its image has no shell), and **the CORS rule** (`PUT`, `GET` from `PUBLIC_URL`, the headers `x-amz-checksum-sha256` and `If-None-Match`, `ETag` exposed) through the S3 API.
    - **Garage needs its own public origin** (e.g. `s3.example.com`, through the same reverse proxy): browsers reach presigned URLs directly, and a path prefix on the app's origin would break their signatures. The server reaches it at the same URL.
    - **In `core`**: the CORS rule documented in `CONFIGURATION.md` (Storage backends), for anyone bringing their own S3 (a `core` docs commit).
    - CI: the smoke test again with the overlay, a chunk through a presigned URL with an `Origin` header.
4. **Two-way sync**: an app password, `rclone config` for WebDAV, `rclone bisync` (first `--resync`, then a cron or systemd timer), its limits (conflicts, deletions, the lock file). Tried against the compose.
5. **First release**: `scripts/release.sh`, the CE image `0.1.0`, release notes naming its `web` and `core`. On the private registry, like every image until 1.0 (going public is decided then, `ROADMAP.md`).

## Out of scope

A bundled reverse proxy or TLS; Helm or other orchestrators; a multi-node Garage; the sync client (V2); the upgrade test (1.0, `ROADMAP.md`).
