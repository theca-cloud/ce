# Global roadmap

From an empty repo to the first CE release. Each step gets its own detailed file (`01. ...`, `02. ...`), written right before implementing it. Scope and design: see `../docs` (`ROADMAP.md` item 4; `decisions.md`: Repository, CI and releases, Configuration, the web app's CORS).

The order: the image first (what everything else runs), tested in CI before anything ships; then the compose a self-hoster runs it with; then the examples around it (S3, proxies, OIDC); the documentation last, once there is something final to describe.

## Steps

| # | Step | Done when |
|---|---|---|
| 1 | **The image** | CI builds the CE image from the pinned `web` (and the `core` its label names), smoke-tests it, and publishes `rc` tags from `dev` |
| 2 | **The compose** | The CE image and Postgres run from `docker-compose.yml` and four generated secret files to the setup link; the `core` and `web` changes it needs are released and pinned |
| 3 | **Examples** | `examples/`: S3 with Garage (smoke-tested in CI), Caddy, Traefik, Authelia (tried by hand) |
| 4 | **Documentation** | `README.md` presents Theca, `SELF-HOSTING.md` runs it, `rclone bisync` included, every command in it tried |
| 5 | **First release** | The CE image `0.1.0` is published, saying which `web` and `core` it holds |

## Contents

1. **The image**:
    - **The pin**: `WEB_VERSION` in the `Dockerfile` (an `ARG` default, the one place it's written). `core`'s version is read from the `web` image's label `org.theca.core` (`docker buildx imagetools inspect`) by `scripts/release-ci.sh`, never written here.
    - **The `Dockerfile`**: `FROM core:<v>`, `COPY --from=web:<v> /web /web`, `ENV WEB_DIR=/web`, labels `org.theca.web` and `org.theca.core`. Distroless, nonroot, `HEALTHCHECK` and entrypoint inherited from `core`'s image. amd64 and arm64: nothing compiled, both are copies.
    - **The smoke test** (`scripts/smoke.sh`, with `curl`, in CI against the freshly built image, Postgres as a service): the server starts and migrates, `/` and a deep link answer `index.html`, `/api/version` is the expected `core`, the setup through the API, a file in and out through WebDAV. `web`'s and `core`'s own suites test the parts: this only proves the pair is assembled right.
    - **Tooling** copied from `../web`: `scripts/ci.sh`, `.woodpecker/` (`ci.yaml`, `release.yaml`), `scripts/release.sh` and `release-ci.sh`, `cliff.toml`, the pre-push hook. The version lives in a `VERSION` file (no `package.json` or `Cargo.toml` here).
2. **The compose** (`docker-compose.yml`, what self-hosters copy):
    - The CE image (by major tag) and Postgres 18 (`--locale-provider=builtin --builtin-locale=C.UTF-8`), on an internal network, Postgres never published. Storage: the filesystem backend, on a volume.
    - **Secrets are files**, one per secret, generated by the self-hoster (`openssl rand`) and mounted read-only through compose `secrets:`: `postgres_password` (Postgres's `POSTGRES_PASSWORD_FILE`), `database_url`, `server.key`, `data.key`. The only plain variable is `PUBLIC_URL`. To check: the mount is read-only and readable by distroless's nonroot user (uid 65532), or the docs say what mode to give the files.
    - **First run**: `docker compose up -d`, then `docker compose logs theca` for the setup link.
    - **In `core`** (its own roadmap step, a breaking `0.x` release with its `BREAKING.md` entry): secrets are read, never written; a missing or empty key file is a startup error naming the variable and `openssl rand -hex 32`. `CONFIGURATION.md` follows, and `scripts/dev.sh` generates its keys.
    - **In `web`**: the wizard keeps one storage and says more are added later from the admin's Storages page; its CI generates the keys instead of writing empty files; a release pinning the new `core`, then pinned here.
3. **Examples** (`examples/`, one folder each, its files and a short README):
    - **`s3-garage/`**: an overlay adding Garage single node, an init service creating the layout, the bucket and the key (through Garage's admin API: its image has no shell), and **the CORS rule** (`PUT`, `GET` from `PUBLIC_URL`, the headers `x-amz-checksum-sha256` and `If-None-Match`, `ETag` exposed) through the S3 API. Garage needs its own public origin (e.g. `s3.example.com`): browsers reach presigned URLs directly, and a path prefix on the app's origin would break their signatures. CI runs the smoke test with it, a chunk through a presigned URL with an `Origin` header. **In `core`**: the CORS rule documented in `CONFIGURATION.md` (Storage backends), for anyone bringing their own S3.
    - **`caddy/`, `traefik/`**: the proxy in front of the compose, for the app's origin and Garage's, with `TRUSTED_PROXIES`.
    - **`authelia/`**: Authelia as an OIDC provider, and the client to register in Theca's admin pages.
    - CI: `docker compose config` on every example; the proxies and Authelia need real domains and certificates, tried by hand.
4. **Documentation**:
    - **`README.md`**, the project's page: what Theca is and does, screenshots (taken by hand, retaken at releases), a quickstart pointing to `SELF-HOSTING.md`.
    - **`SELF-HOSTING.md`**, running it: the secrets and their commands, first run and the setup link, **a reverse proxy with HTTPS is required** (not bundled: the web app downloads through a Service Worker, which needs a secure context), S3, OIDC, backups and restore (`pg_dump`, the files volume, `secrets/`: `data.key` lost = every TOTP set up again), upgrades (pull, restart: migrations at startup, transactional), and two-way sync with `rclone bisync` (an app password, `rclone config` for WebDAV, the first `--resync`, a timer, its limits). It links to `examples/` rather than embedding them.
5. **First release**: `scripts/release.sh`, the CE image `0.1.0`, release notes naming its `web` and `core`. On the private registry, like every image until 1.0 (going public is decided then, `ROADMAP.md`).

## Out of scope

A bundled reverse proxy or TLS; Helm or other orchestrators; a multi-node Garage; the sync client (V2); the upgrade test (1.0, `ROADMAP.md`).
