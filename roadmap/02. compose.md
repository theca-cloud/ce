# Step 02: The compose

Goal: `docker-compose.yml`, what a self-hoster downloads to run the CE: the image and Postgres, secrets as read-only files, the filesystem storage on a volume. The smoke test runs this very file, so the compose people copy is the one CI proves. `core` 0.17.0 (secrets only read) and `web` 0.2.0 (one storage in the wizard) are pinned already.

## `docker-compose.yml`

```yaml
name: theca

services:
  postgres:
    image: postgres:18
    restart: unless-stopped
    environment:
      POSTGRES_USER: theca
      POSTGRES_DB: theca
      POSTGRES_PASSWORD_FILE: /run/secrets/postgres_password
      POSTGRES_INITDB_ARGS: --locale-provider=builtin --builtin-locale=C.UTF-8
    secrets: [postgres_password]
    volumes: [db:/var/lib/postgresql]
    healthcheck: {test: pg_isready -U theca -d theca, interval: 5s, retries: 12}

  theca:
    image: git.pband.ch/theca/ce:0.1.0
    restart: unless-stopped
    depends_on: {postgres: {condition: service_healthy}}
    environment:
      PUBLIC_URL: ${PUBLIC_URL:?PUBLIC_URL is missing: the HTTPS address users open, in .env}
      DATABASE_URL__FILE: /run/secrets/database_url
      SERVER_KEY__FILE: /run/secrets/server.key
      DATA_KEY__FILE: /run/secrets/data.key
      # TRUSTED_PROXIES: your reverse proxy's address (SELF-HOSTING.md)
    secrets: [database_url, server.key, data.key]
    volumes: [data:/data]
    ports: ["127.0.0.1:8080:8080"]

secrets:
  postgres_password: {file: ./secrets/postgres_password}
  database_url: {file: ./secrets/database_url}
  server.key: {file: ./secrets/server.key}
  data.key: {file: ./secrets/data.key}

volumes:
  db:
  data:
```

(Written out in block style in the file, with comments.)

- **The image's tag is the exact CE version** (`0.1.0`), not a moving one, until 1.0: `core`'s migration is rewritten in place before 1.0 (`decisions.md`, Schema and migrations), so an upgrade may mean starting over, and must be chosen, not pulled by a restart. From 1.0 on, the major tag (`ce:1`): upgrades are then forward migrations. `scripts/release.sh` writes the tag with `VERSION`, so the compose on `prod` always names its own release.
- **`PUBLIC_URL`** from `.env` (Compose reads it by itself), the only plain variable; missing, `docker compose up` stops with the message. No `.env.example`: one line, shown in the docs.
- **Secrets are files in `./secrets/`**, created by the self-hoster before the first start (the commands in `SELF-HOSTING.md`, step 04, and in the compose's header comment until then). Compose mounts them read-only at `/run/secrets/<name>`; mode `644` so the server's user (uid 65532) reads them (checked in step 01's CI). A missing file stops `docker compose up`; an empty one stops the server, naming it (`core` 0.17.0).
- **Named volumes**, not bind mounts: `data` starts with the image's `/data`, owned by the server's user, so the filesystem storage is writable with nothing to `chown`. A bind mount works too, owned by 65532 (said in the docs). Postgres's volume at `/var/lib/postgresql`, the path its 18 image expects (data in a versioned subdirectory, ready for `pg_upgrade`).
- **Published on `127.0.0.1:8080` only**: the reverse proxy on the same host reaches it; nothing reaches the plain-HTTP port from outside. A proxy in Docker (Traefik, step 03's examples) joins the network instead and the `ports` go.
- **No `SETUP_OPEN`**: the setup link with its token is in the logs (`docker compose logs theca`), the instance safe until its admin opens it.
- **`postgres:18`**: minor updates come with pulls, a major one is a `pg_upgrade` (documented in step 04).
- `restart: unless-stopped` on both; the image's `HEALTHCHECK` is `core`'s.

## The smoke test runs it

`scripts/smoke.yml` becomes an override of `docker-compose.yml` (`docker compose -f docker-compose.yml -f scripts/smoke.yml`), changing only what a test must:

- the image: `theca-ce:smoke`, the one just built;
- `SETUP_OPEN: "true"`: the test sets it up through the API (it can't click the logged link);
- the secrets: from `.smoke/` (the workspace, where a remote daemon finds them);
- `ports: !override` on `SMOKE_BIND:SMOKE_PORT`, and the faster health checks;
- `PUBLIC_URL` from the environment (`http://localhost:8099`).

Everything else (Postgres's settings, the secrets' names and targets, the volumes) is the shipped file's. The checks stay step 01's. Also: `docker compose config -q` on the compose alone, with a `PUBLIC_URL`, in `scripts/ci.sh` (a broken file fails before the image is built).

## Release

- `scripts/release.sh` writes the version into the compose's image tag (`ce:X.Y.Z`) with `VERSION`.
- The Gitea release attaches `docker-compose.yml`: a self-hoster downloads the release's compose, which names that release.

## Done when

- `scripts/ci.sh` passes locally and in CI, the smoke test running `docker-compose.yml`.
- By hand, from an empty folder: the compose, `.env`, the four secret commands, `docker compose up -d`, the setup link from the logs, the wizard in a browser (on `localhost`, a secure context), a file uploaded and downloaded.
