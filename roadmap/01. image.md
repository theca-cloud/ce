# Step 01: The image

Goal: the CE image built from the pinned `web` and the `core` it names, proven to work as a pair before anything is published, with the release tooling of the other repositories. `dev` publishes `rc` tags; `prod` is step 05's.

## Files

```
Dockerfile              the image: core's, plus web's build
VERSION                 the CE version (0.1.0 until step 05 releases it)
scripts/core-version.sh the core a web image is for (its label, read from the registry)
scripts/smoke.sh        builds the image, runs it with Postgres, checks it with curl
scripts/smoke.yml       the compose smoke.sh runs (replaced by the real one in step 02)
scripts/ci.sh           what CI and the pre-push hook run
scripts/release.sh      prepares a release (git-cliff)
scripts/release-ci.sh   the release pipeline's steps: tags, publish
scripts/install-hooks.sh, .githooks/pre-push
.woodpecker/ci.yaml, .woodpecker/release.yaml
cliff.toml, CHANGELOG.md (written by the first release)
```

Copied from `../web` and trimmed where they differ: no npm, the version in `VERSION`.

## The `Dockerfile`

```dockerfile
ARG WEB_VERSION=0.1.0
ARG CORE_VERSION
FROM git.pband.ch/theca/web:${WEB_VERSION} AS web
FROM scratch AS dirs
WORKDIR /data/files
FROM git.pband.ch/theca/core:${CORE_VERSION}
ARG WEB_VERSION CORE_VERSION
COPY --from=web /web /web
COPY --from=dirs --chown=65532:65532 /data /data
ENV WEB_DIR=/web
LABEL org.theca.web=${WEB_VERSION} org.theca.core=${CORE_VERSION}
```

- **`WEB_VERSION` is the pin**, its one place. **`CORE_VERSION` has no default**: it is never written here, only read from the `web` image's label `org.theca.core` (`scripts/core-version.sh`) and passed in. A build without it fails at `FROM` rather than taking some `core`.
- **`/data` owned by the image's user** (distroless `nonroot`, uid 65532): a named volume mounted there starts with the image's ownership, so the server can write the filesystem storage (`/data/files`) without the self-hoster changing anything. Distroless has no shell to `mkdir`: an empty directory from a `scratch` stage, made by its `WORKDIR` (nothing runs, so nothing is emulated for arm64).
- Everything else is inherited from `core`'s image: distroless static, `nonroot`, `LISTEN_ADDR`, `EXPOSE 8080`, the `HEALTHCHECK` with its start period, the entrypoint. `TMPDIR` stays `/tmp` (WebDAV's spool, `CONFIGURATION.md`).
- **amd64 and arm64**: nothing runs in any stage, so the arm64 build is copies (no QEMU-compiled code).

## The core version (`scripts/core-version.sh`)

`scripts/core-version.sh [web version]` prints the `core` version the `web` image is for: the registry's API with `curl` and `jq` (a bearer token from `GITEA_TOKEN`, the image index, one platform's manifest, its config's `org.theca.core`), the version defaulting to the `Dockerfile`'s `WEB_VERSION`. Through the registry, not `docker buildx imagetools inspect`: the release pipeline's tools image has no Docker, and the same script runs everywhere. Fails loudly when the label is missing (a `web` image older than 0.1.0).

## The smoke test (`scripts/smoke.sh`)

Proves the pair is assembled right, nothing more: `core`'s and `web`'s suites test each side.

1. `docker build` the image for the local platform, `CORE_VERSION` from `core-version.sh`, tagged `theca-ce:smoke`.
2. Throwaway secret files (a password, the database URL, two keys) and `docker compose -f scripts/smoke.yml up -d --wait`: Postgres 18 (builtin `C.UTF-8`) and the image, `SETUP_OPEN=true`, a named volume on `/data`. `--wait` passes once the image's own `HEALTHCHECK` does: migrated and listening.
3. With `curl`:
    - `/` and a deep link (`/some/deep/link`) answer the web's `index.html`; an unknown `/api/...` path stays `404`.
    - `/api/version`'s `server` is the expected `core`.
    - The setup through the API (an admin, an organization, the filesystem storage on `/data/files`), a library, an app password.
    - WebDAV: a file `PUT` into the library, `GET` back identical (proves `/data/files` is writable by the server).
4. Down with its volumes, whatever happened (`trap`). `--keep` leaves it running to look at.

The host it reaches is `SMOKE_HOST` (default `localhost`; in CI the Docker daemon's service name), the port published on it.

## CI (`.woodpecker/ci.yaml`)

- **The smoke test runs against a real Docker daemon**: `docker:dind` as a detached step (not a service: steps share the workspace, so the daemon bind-mounts the secret files at the path the smoke step wrote them; privileged, so **the repository is marked trusted** in Woodpecker, an admin setting), the step on `docker:cli` (`curl` and `jq` added) with `DOCKER_HOST` pointing at it, logged in to `git.pband.ch` (`gitea_user`, `gitea_token`) to pull `core` and `web`. It tests the very `Dockerfile` that is published, and step 02 and 03 reuse it for `docker compose` on the real compose and the examples. Rejected: pushing a throwaway tag to test it (the registry fills with them, and the test comes after the push); running `core`'s image with `web`'s files extracted (doesn't test the `Dockerfile`, and leaves the compose untestable).
- When: as `web`'s, every push and pull request when something tested changed (not `**/*.md`, `roadmap/**`, the local-only scripts), not the release merge coming back into `dev`; manual runs always.
- `scripts/ci.sh` is the smoke test (no other check yet: no code); the pre-push hook runs it (a local Docker and `docker login git.pband.ch`).

## Releases (`.woodpecker/release.yaml`, `scripts/release.sh`, `release-ci.sh`)

As `web`'s, after `ci`:

- **`tags`**: the tags in `.tags` (`X.Y.Z-rc`, `X.Y-rc`, `X-rc`, `rc` on `dev`; `X.Y.Z`, `X.Y`, `X`, `latest` on `prod`, refusing a version already released), and `CORE_VERSION`'s default written into the `Dockerfile` (`sed`): the buildx plugin's build arguments are static, as `web` found.
- **`image`**: `woodpeckerci/plugin-docker-buildx`, `linux/amd64,linux/arm64`, to `git.pband.ch/theca/ce`.
- **`publish`** (`prod`): the tag and the Gitea release, its notes saying `web X` and `core Y` (links to their releases), then this version's changelog.
- `scripts/release.sh`: the next version from git-cliff, written to `VERSION` and `CHANGELOG.md`, committed `chore(release): X.Y.Z`. The first release is `VERSION`'s `0.1.0` (step 05).
- **Bumping `web`** is a commit changing `WEB_VERSION`, `build: web X.Y.Z (core A.B.C)`: the changelog then says what each CE holds. `fix:` when the new `web` or `core` is a fix, `feat:` when it brings features, so the CE's version follows what users get.

## Done when

- `scripts/ci.sh` passes locally and in CI on `feat/image`.
- Merged into `dev`: its pipeline publishes `git.pband.ch/theca/ce:0.1.0-rc` (and `rc`, `0-rc`, `0.1-rc`) for both platforms, its labels naming `web 0.1.0` and `core 0.16.0`.
- `docker run` of that image on arm64 (a Mac) starts and serves the app.
